Three queries

Covering

The composite index already stores user_id and created_at. A query that needs only those columns can be an Index Only Scan: Postgres does not read the table page. body is not in the index, so selecting it still reads the table (a heap fetch) after the index finds the rows.

LSM tree

Postgres keeps the B-tree above. An LSM tree is the storage format of the whole table, sorted by the primary key, not an extra index on any column. A write appends to a log and lands in a small sorted table in RAM (the memtable). When that table is full, it is frozen into a sorted file on disk (an SSTable). A read checks RAM first, then the newest file. A bloom filter and compaction are how a real engine avoids opening every file. This button does not run those.

Geospatial

The restaurants table is latitude and longitude, with a B-tree on each: CREATE INDEX idx_lat ON restaurants(latitude) and CREATE INDEX idx_lng ON restaurants(longitude). Four restaurants sit in this database. The question is which ones are within 200 meters of the Ferry Building.

  • idx_lat / idx_lng. Each index is one strip. Using both is a rectangle in degrees.
  • Geohash. The second button turns lat/lon into a short code, one character at a time, then retrieves restaurants whose code starts with that prefix.
  • Quadtree. Split the map into four until a cell is small. Walk squares that overlap the search square, then check distance.
  • R-tree. Nested boxes. PostGIS GiST checks the real 200 meter disk.
Click the button. Each index lists which restaurants it returns for “within 200 meters.”

Inverted index

Full search reads every body looking for redis. There is no map from the word to the rows. The word index is that map: redis points at the document ids. Postgres GIN is a real inverted index. Elasticsearch stores the same kind of map, and adds ranking and typo tolerance. This page keeps both sides in Postgres so you can see the scan and the map.

What you should see

  • No composite index. All three plans start with a sequential scan. Postgres reads the table.
  • After the index. user_id = 42 and user_id = 42 AND created_at … use the index.
  • Date only. June 1 on created_at alone still scans the table.
  • Covering. SELECT user_id, created_at is an Index Only Scan. SELECT body uses the index to find rows, then reads body from the table.
