Store reference — what each piece is for

Durable truth lives in Postgres. Live hops and counters use Redis. Open sockets stay in each chat server process. Scroll up to watch them change.

Postgres Durable tables

users
Who can chat. Primary key id (lee, kim, ada). Seeded once. Rarely changes in this lab.
chats
One row per conversation. Holds id, display name, and created_at. Example ids: lee-kim, trip.
chat_members
Who belongs to which chat. Key (chat_id, user_id). Send and fan-out read this list to know every recipient user.
clients
Devices for a user (lee-phone, kim-laptop). Key id. Connect and ack name a clientId, not only a user. Multi-device needs this split.
messages
Source of truth for every message. Columns include chat_id, per-chat seq, sender_id, body, optional media_key. Unique on (chat_id, seq). Offline drain reads from here.
device_cursors
How far each device has confirmed in each chat. Key (client_id, chat_id), value last_seq. Sender advances on send. Recipient advances only on ack. Drain sends rows with seq > last_seq.
last_seen
When the user went fully offline (no device left connected). Key user_id. Optional for "last seen" UI. Not used for delivery.

Survivable crash: messages and cursors stay. Redis Pub/Sub events do not.

Redis Live bus and helpers

Pub/Sub channel user:{id}
Live hop to one user. On send, publish the new message here. Every chat server that has that user online is subscribed. That server writes into its local mailbox / socket. Ephemeral: if no subscriber is listening, the publish is gone.
Pub/Sub channel chat:{id}
Optional group fan-out path for large chats (hot-chat variant). Same idea as user channels, keyed by chat instead of user.
subscriptions (A / B)
Which channels each logical server currently listens to. Grows when you connect a device. Shrinks when that server has no local device left for that user.
user:{id}:server
Presence helper string: which server last claimed this user (example user:kim:server → B). Not the socket. Helps ops and demos. Delivery still uses Pub/Sub plus the local connection map.
chat:{id}:seq
Atomic counter via INCR. Assigns the next seq for that chat before the Postgres insert. Keeps sequence numbers unique under concurrent sends.
Pub/Sub log
Lab-only history of SUBSCRIBE, PUBLISH, and RECEIVE. Production Redis does not keep this log for you.

Redis wins for speed and fan-out. Postgres wins for "Kim was offline; give her everything after last_seq."

Chat servers A / B Process-local (not a table)

clientToSocket
In-memory map on that process only: clientId → { userId, socket }. Redis never stores the socket. Cross-server Kim lives only on B's map.
userToClients
Reverse lookup on that same process: userId → [clientIds]. Used when a Pub/Sub event arrives and the server must push to every local device for that user.
device mailbox
Lab stand-in for "bytes on the wire to the phone." Shows via: user-channel (online) or via: drain (catch-up after reconnect). Seeing a row here is not the same as moving the cursor.

Try: Lee on A, Kim on B, send once. Watch messages (Postgres), Pub/Sub RECEIVE on B, Kim mailbox, then Ack all to move Kim's cursor.

Cassandra Design 2 tables

messages_by_chat
Same facts as the Postgres messages row. Key ((chat_id, bucket), seq). The partition key (chat_id, bucket) picks the node through its token. The clustering key seq sorts rows on disk inside that partition. Table option default_time_to_live = 2592000 expires rows after 30 days.
bucket
seq / 5 in this lab. It stops one old chat from growing one partition forever. Drain reads each bucket from last_seq + 1 up to the current seq. Discord buckets by about 10 days of time instead.
device_cursors_by_client
Key ((client_id), chat_id). One partition per device. Drain reads it by device. A plain UPDATE is an upsert with no read. The last write wins, so a late ack can move the cursor back. The device then gets a duplicate, and the client drops it by message id.
LWT
A lightweight transaction: UPDATE ... IF last_seq < ?. It runs Paxos, which takes four round trips instead of one. It keeps the cursor moving forward. It costs latency on every ack.
Not in Cassandra
seq still comes from Redis INCR. Cassandra has no safe per-chat counter for this. The roster tables stay in Postgres. They change rarely, and create-chat needs one transaction.

Try: send 6 messages to lee-kim. Watch the partition card get a second row, (lee-kim, 1). Then disconnect Kim, send, and connect. The connect response lists each partition the drain read.

Design 1 vs Design 2 — the same chat, two message stores

messages key
Postgres: id plus UNIQUE (chat_id, seq). Cassandra: ((chat_id, bucket), seq).
send write
Postgres: one insert on the primary. Cassandra: one append to the partition, with no read first.
drain read
Postgres: one index range, seq > last_seq. Cassandra: one range read per bucket from last_seq + 1 up to the current seq.
cursor update
Postgres: GREATEST(old, new), so a late ack is ignored. Cassandra: an upsert, so a late ack moves the cursor back. Use an LWT to stop that.
transaction
Postgres: the message and the cursor can share one transaction. Cassandra: two separate writes. At least once covers a crash between them.
30-day retention
Postgres: a batch delete, or dropping daily partitions. Cassandra: a TTL on each row, then compaction removes it.
scale out
Postgres: you build shard routing by chat_id. Cassandra: add nodes, and the token ring moves the partitions.
when it wins
Postgres: up to about a few thousand writes per second, or a team that runs MySQL or Postgres well. Cassandra: about 40,000 messages per second, append-only writes, reads by key.

When tables grow — split or leave alone

Interview default at the Hello Interview scale: move messages to Cassandra, keyed by chat_id plus a bucket (design 2). Most other tables stay one piece until a measured pain appears.

messages
Split first. At about 100,000 writes per second, move to a wide-column store such as Cassandra. Key ((chat_id, bucket), seq): one chat stays together, a time bucket bounds the partition, and seq sorts rows for the drain range read. A TTL drops rows after 30 days. Sharded Postgres by chat_id is the other valid path. Do not shard by sender_id. Then drain must read from every shard.
device_cursors
Split with the device or the chat. Often co-locate with messages by chat_id, or shard by client_id / user_id. Key stays (client_id, chat_id). Grows with devices × chats, not with every message.
chat_members
Split only if huge. Prefer shard by chat_id (same as messages) so "who is in this chat" is one lookup on send. Secondary index or cache for "all chats for user" if that query is hot.
chats
Usually no split. One row per conversation. Millions of chats still fit one primary for a long time. Shard by chat_id only if chat metadata itself is huge.
clients
Usually no split. A few devices per user. Shard by user_id only at very large account counts.
users
Usually no split in the chat service, or shard by user_id in a shared account store. Not on the hot send path beyond a membership check.
last_seen
No split needed for delivery. One row per user. Can live in Redis or a small table. Optional display only.
Redis Pub/Sub
Shard the cluster by channel name (user:{id}), not by storing message history. Presence keys user:{id}:server and seq keys chat:{id}:seq follow the same hash. Seq must stay with that chat's message shard logically (same chat id).
Local socket maps
Scale out chat servers (more A/B processes). Each process keeps only its own sockets. Not a database partition.

Rule of thumb: partition on the key your hottest query already uses. For chat history that key is chat_id.
