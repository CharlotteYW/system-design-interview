Rate limiter

The check runs in this API (middleware), then Redis. Rules are loaded once from src/rules.yaml at startup. Production algorithm is sliding window counter. This page runs all five so you can compare. POST /api/work is 5 per 10s and writes Postgres only when allowed. GET /api/ping is 20 per 10s. GET /api/edge is 10 per 60s. 

Results show up here.

What each algorithm means

The dropdown runs that algorithm in Redis. Read the matching card, then try the buttons. Use a new client id when you switch algorithms so the counters do not mix.

Fixed window. Redis keeps one integer for the current clock bucket and INCRs it. The bucket resets when the clock crosses the window, not when your first call happened.

Example, limit 10 per 60s. Ten calls at 59.9s fill the 0–60s bucket. At 60.0s a new bucket starts at 0, so ten more are allowed. That is 20 calls about 0.1s apart. Press “Edge” on Fixed window: allowed=10, then allowed=10.

Sliding window counter. Redis keeps this bucket and the previous one. The previous count is multiplied by how much of it still sits inside the last window: previous × (window − elapsed) / window + current.

Example, same 10 at 59.9s. At 60.0s the previous bucket still counts in full (elapsed is 0), so the estimate is 10. The next ten calls are 429. Press “Edge” on Sliding window counter: allowed=10, then denied=10. A few seconds later the previous bucket weighs less, so a few new calls can pass. This is the one to ship.

Sliding window log. Redis stores the timestamp of each allowed call in a sorted set and counts timestamps newer than now − window.

Example, same edge. At 60.0s all ten timestamps from 59.9s are still inside the last 60s, so the next calls are 429. Same answer as the counter on this edge, with one Redis entry per allow instead of two integers. Fine in this lab. Heavy at 10k QPS.

Token bucket. Redis stores how many tokens are left and when they were last refilled. The bucket starts full. Each allow spends one token. Tokens come back at limit / window.

Example, POST /api/work is 5 per 10s, so the bucket starts with 5 tokens and refills one token about every 2s. Press “Send 8 work calls”: five 200s (a row in Postgres each time), then 429s. Wait about 2 seconds and one more work call can succeed, without waiting for a clock minute to end.

Leaky bucket. Redis stores a water level and the last leak time. The bucket starts empty. Each allow adds 1. The level falls at limit / window. A call that would rise past the limit is a 429, and the level does not rise.

Example, work is capacity 5, leaking about one unit every 2s. Five fast work calls fill it (200). The sixth is 429 until some level has leaked away. This page does not hold the HTTP connection in a queue; it rejects when the bucket is full. That steady leak is what people mean by “smooth.” The token bucket instead lets you spend a saved-up burst.

Redis down, or already over the cap. If Redis errors, this process uses a smaller fixed window: limit ÷ 4. After Redis has already returned over the limit, this process remembers “blocked until the window ends” and answers 429 without another Redis call. The header X-Rate-Path says redis, local-block, or local-emergency.

Example, work limit 5. Calls 1–5 are 200 path=redis. Call 6 is 429 path=redis. Calls 7 and 8 are 429 path=local-block.
