Unique ID generator

Four ways to mint an ID. Each button runs servers A and B and prints the steps. The 64-bit generator is the one this chapter keeps. The others show what it avoids.

Database counter

  1. Server A or B asks Postgres for nextval('id_seq').
  2. Postgres adds one to the sequence and returns that integer. The next caller cannot receive it.
  3. That integer is the ID. There is no timestamp and no worker number inside it.

Ticket ranges

  1. Each server keeps a small block in memory. This lab uses blocks of 4.
  2. When the block is empty, the server asks Postgres to reserve the next 4 integers and moves the global cursor past them.
  3. Further IDs are handed out from memory until the block is used. A crash throws away the unused tail.

Random UUID, version 4

  1. The server draws 16 random bytes, 128 bits.
  2. The high 4 bits of byte 6 are set to 0100, so the version is 4. In the printed form that is the first character of the third group.
  3. The high 2 bits of byte 8 are set to 10, the RFC variant. Every other bit stays random.
  4. No clock and no worker number are stored. Two IDs do not sort by time.

64-bit time, worker, and sequence

Rule. One ID is one integer of 64 bits. The top bit stays 0. The other 63 bits are three fields, high to low: 41 bits of time, 10 bits of server, 12 bits of sequence.

ID = (time × 2^22) + (server × 2^12) + sequence

This is a sum of those three numbers. The decimal digits are not pasted together. The code writes the same sum as (time << 22) | (server << 12) | sequence, because the shifts put the three fields in different bits, and adding them does not make those bits overlap.

This example prints as 18 digits. The largest ID prints as 19 digits, because the top bit stays 0 and 2^63 − 1 is 9223372036854775807. There is no rule that assigns each decimal digit its own field. The digits are the base-10 spelling of that one sum.

time      169163200000 × 4194304 = 709521886412800000
server    0 × 4096               =                  0
sequence  0                      =                  0
--------------------------------   ------------------
sum                                709521886412800000
digit                              123456789012345678

time, 41 bits server, 10 bits sequence, 12 bits

  1. Read the clock in milliseconds. Subtract the epoch 2020-01-01. That delta uses 41 bits. It is the left part of the integer.
  2. This server’s worker number uses the next 10 bits. It sits between the time and the sequence.
  3. The sequence for this millisecond uses the last 12 bits. A new millisecond starts it at 0. Another ID in the same millisecond adds one, up to 4095.
  4. Pack (delta << 22) | (worker << 12) | sequence. The sign bit stays 0 so the integer is positive.

Same time, same sequence 0. A is server 0. B is server 1. No single decimal digit is the server. The server is those 10 bits. In this pair the server change shows up in the last 5 digits.

A 709521886412800000
B 709521886412804096
time, same server + sequence

00000 is 0 << 12, server 0 and sequence 0. 04096 is 1 << 12, server 1 and sequence 0. 1 << 12 is 4096. Server 0 is present: its 10 bits are 0000000000. That value is 0, so it does not print its own digits. The last 00000 is those server bits and the sequence bits, both zero, added together. The sequence bits stay 000000000000. The server bits are 0000000000 versus 0000000001.

One millisecond on server A, server 0. The base ID is 709521886412800000. Sequence 1 through 1000 adds 1 each time, so the ID is the base plus the sequence. The time digits stay 7095218864128. The last five digits are the sequence. 

sequence      ID
1             709521886412800001
2             709521886412800002
3             709521886412800003
10            709521886412800010
100           709521886412800100
1000          709521886412801000

Every integer between those rows is also an ID from A in that same millisecond. Sequence 1000 is still under the cap of 4095.

Clock moves backward

Server A remembers the millisecond of its last ID. If the wall clock jumps back 5 seconds, the next ID keeps that millisecond and adds one to the sequence. The new integer still sorts after A’s previous ID. NTP can run in the background. It is not called while minting.

Worker slots

The slot table is a sign-up sheet with one row per server number, 0 through 1023. A starting server writes its name on the first empty row and then uses that row number in the sum. A second server finds that row taken and writes on the next row. Two servers cannot hold the same row, so they cannot put the same server number into the sum. In this lab the sheet is a Python list of 1024 pairs, (owner, expires), built in memory when you click the button below. It is not a YAML file. In production the same 1024 rows can sit in Postgres, DynamoDB, or ZooKeeper/etcd. Postgres is enough, because the sheet is written at startup, not on every ID. ZooKeeper or etcd is the usual lease, because the row disappears when the process dies. The four generator buttons skip the sheet and use fixed numbers, A = 1 and B = 2. The buttons above hard-code A = 1 and B = 2. This button replays the startup assignment with the first free slots, 0 and 1.

One millisecond fills up

One worker can issue 4096 IDs in a single millisecond, sequence 0 through 4095. The next ID waits for the following millisecond and starts the sequence at 0. 100,000 IDs/s is about 100 in a typical millisecond, so the bit layout stays.

One app server dies

IDs already returned stay valid. Other workers keep minting. The crash skips at most 4096 IDs, the rest of that one millisecond on that server. If the server dies 1 second into a 30-second lease, slot 0 then sits unused for about 29 seconds. Those unused numbers are gaps, not failed requests. At 10,000 IDs/s the other servers cover that gap. The time field lasts about 69 years, so 29 seconds is small. On the ticket path, the rest of the block is wasted and the next server starts after it.

Postgres does not answer

The counter and the ticket path both stop, because they need Postgres. The 64-bit path keeps minting in memory. This button simulates the outage. The database container stays up.
